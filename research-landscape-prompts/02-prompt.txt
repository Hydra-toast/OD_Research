Research Landscape — 02/14 공통 데이터와 예시 공급자

[이전 단계 이어받기]
먼저 AGENTS.md와 docs/PRODUCT_CONTRACT.md, docs/PROGRESS.md, docs/DECISIONS.md, docs/TEST_MATRIX.md를 읽어라. 계약 파일이 없다면 1번이 아직 적용되지 않은 것이므로 전제를 추측하지 말고 필요한 1단계 기록부터 복원하라. 기존 사용자 변경과 작동 기능을 보존하라.
지정된 이번 단계만 구현·검증하고 다음 번호를 자동 실행하지 마라. 선행 결손은 이번 작업에 필요한 범위에서 먼저 수정하라. 키·계정이 없으면 독립 구현과 고정 응답 테스트를 진행하되 실제 연동은 미검증으로 남겨라. 보안이나 데이터 무결성 전제는 우회하지 마라.

2/14단계: 데이터 계약과 교체 가능한 공급자 구조만 구현하라.

[작업]
- 현재 script.js를 읽고 기존 작동을 유지하면서 상태·데이터·렌더링·저장·공급자 모듈을 나눈다. 초기부터 대규모 구조를 만들지 않는다.
- JSDoc 타입과 런타임 스키마 검증을 정의한다. 엔티티: Project, LabProfile, Paper, SourceDocument, Evidence, Direction, Claim, Selection, Feedback, AnalysisVersion, Job.
- Project에 원래 입력·현재 범위·제외 조건·검색어·dataMode를 둔다. 논문은 DOI/providerId, 제목, 저자, 연도, 저널, nullable 인용수, 수집 시점·출처를 가진다.
- Evidence는 문서 버전, 발췌, 페이지/절/그림/표 위치를 nullable로 가진다. Claim은 문장·조건·해석·evidenceIds·reviewState·수정 이력을 가진다.
- 자료 접근 상태(metadata/abstract/fulltext)와 자료 출처(provider/user/example)를 분리한다. 주장에는 출처 발췌 연결 여부, AI 해석 여부, 사용자 확인 여부, 추가 확인 필요 상태를 각각 기록한다.
- 비교 셀의 빈값 이유는 ‘자료에서 찾지 못함 / 원문 미확보 / 추출 실패 / 적용 안 됨’으로 구분한다.
- PaperProvider(search/resolve), AnalysisProvider(analyze), ProjectRepository(load/save/list/delete)의 공통 인터페이스를 만든다. P0는 예시 공급자만 구현한다.

[예시와 테스트 자료]
- EUV PR, ALD, HBM의 사전 작성 예시를 만든다. 충분한 자료 사례는 최소 8개 문헌 항목, 부족 사례는 3개로 한다.
- 가상 항목 ID는 example: 접두사를 사용하고 실제 DOI·저자·학술지·외부 논문 URL을 만들어 넣지 않는다. 표시 제목도 ‘예시 논문 A’처럼 가상임을 드러낸다.
- 예시 발췌에 위치를 넣을 경우 자체 작성 예시 문서 안에서 실제로 일치하게 한다. 실제 연구 근거로 저장·내보내지 않는다.
- 고정 응답 테스트 공급자에 정상/0건/429/초록 없음/원문 없음/추출 실패/부분 성공/저장 실패/지연 응답을 넣는다. 공급자 모드 전환은 명시적으로만 이루어진다.
- 실검색 실패를 예시 공급자로 바꾸는 fallback을 만들지 않는다.

[완료 기준]
ID 참조·스키마·중복 정리·접근 상태·모드 혼합 차단을 단위 테스트한다. 제목이 같다는 이유만으로 다른 논문을 합치지 않는다. 예시 공급자와 이후 실공급자가 같은 계약을 사용하는 것을 확인한다. package scripts에 check와 test를 만든다. 이후 UI에서 쓰지 않는 거대한 추상화는 추가하지 않는다.

[단계 종료]
이번 변경, 검사 결과, 미완료·외부 미검증, 필요한 설정, 다음 번호를 docs/PROGRESS.md에 갱신하고 결정이 달라졌으면 docs/DECISIONS.md에 근거를 남겨라. 수행하지 않은 검사·연동·저장을 완료라고 보고하지 마라. 필수 조건이 실패하면 다음 입력 전에 해결할 항목을 밝혀라. 최종 답변은 구현 결과·확인 결과·남은 항목·다음 번호만 간결하게 작성하라.
