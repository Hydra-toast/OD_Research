Research Landscape — 01/14 기존 저장소 확인과 개발 기준 고정

이번에는 1/14단계만 실행하라. 대상은 Research Landscape이며, 이전 장문 프롬프트를 읽지 않았어도 아래 내용만으로 시작할 수 있다.

[목표]
새 연구 주제를 받은 석사 신입과 초기 연구자가 분야의 갈래, 먼저 읽을 논문과 이유, 연구실과의 연결, 랩미팅에서 설명할 근거를 찾는 웹 서비스를 만든다. 초기 데이터 검증은 반도체 중심이며 EUV photoresist, High-k dielectric, ALD, HBM, GAA transistor, SiC, 2D semiconductor 등 입력을 허용한다. 장기적으로 배터리·디스플레이·화학/소재·공학으로 확장 가능한 데이터 구조를 둔다.
실제 작업 화면은 ‘탐색’과 ‘랩미팅 준비’ 두 개다. 연구실 정보·근거·범위 수정은 보조 패널이다.

[지금 먼저 확인]
- 현재 작업 경로, AGENTS.md, Git 상태, 실행 방법, index.html/script.js/styles.css와 기존 상호작용을 확인한다.
- 참고 저장소는 C:/Users/USER/Dev/Research_Page다. 다른 저장소에서 실행 중이면 임의로 그곳을 수정하지 말고 실제 연결된 프로젝트를 확인한다.
- 평가 문서에는 styles.css가 없다고 적혀 있었으나 후속 확인에서는 존재했다. 파일 유무와 색상은 현재 파일을 기준으로 판단한다.
- 사용자 변경을 덮어쓰거나 reset하지 않는다. Git을 사용할 수 있으면 현재 diff를 확인하고, 없으면 수정할 원본을 work/baseline에 보관한다. 자동 커밋은 하지 않는다.

[이번 실행 묶음의 고정 결정]
- 프런트엔드: 기존 HTML/CSS/JavaScript 유지. ES modules와 파일 분리는 허용. Next.js/React로 이전하지 않는다.
- 서버: 8단계부터 Node.js + Express, JavaScript ESM. 프런트엔드와 API는 같은 출처로 서비스한다.
- 타입 확인: JSDoc + TypeScript checkJs. 단위/통합 테스트는 Vitest, UI 테스트는 Playwright.
- 영속 저장: P0는 IndexedDB, P1은 Supabase PostgreSQL + Supabase Auth 이메일/비밀번호, P2 파일은 Supabase 비공개 Storage.
- 로그인 없는 P0는 해당 브라우저의 예시 프로젝트만 저장한다. 이를 사용자 계정 보안이나 서버 접근 제어라고 부르지 않는다.
- 실검색: Semantic Scholar, DOI/서지 보완: Crossref. 원문 경로: 사용자 업로드 또는 Semantic Scholar openAccessPdf 후보 중 접근·이용 조건을 확인한 자료.
- AI 공급자: OpenAI Responses API. 서버 환경변수 OPENAI_API_KEY, OPENAI_MODEL=gpt-5.4-mini. 이용 불가 시 모델을 몰래 대체하지 말고 해당 기능의 설정 필요 상태를 남긴다.
- 브랜드: Atlas를 Research Landscape로 교체한다. 기존 헤더는 ‘사용 예시 / 저장한 조사’로 통합하고, 인증 연결 후에만 로그인·계정을 노출한다.
- 기존 ‘이용 범위’/요금 섹션은 제거하고 FAQ로 통합한다. 무료 탐색과 향후 유료 근거 정리라는 상품 가설은 문서에 보존한다. 가격·결제·유료 잠금은 이번 범위 밖이다.
- 기존 리그닌·전고체·페로브스카이트 랜딩 예시는 EUV PR·ALD·HBM으로 교체한다.
- 디자인은 3단계의 통일 토큰을 전 화면에 적용한다. 과거 채도를 추측하거나 누락된 CSS를 복원했다고 주장하지 않는다.

[항상 지킬 제품 원칙]
실제 논문·DOI·수치·원문 위치를 지어내지 않는다. 예시 데이터에는 ‘가상 예시 · 실제 논문 아님’을 표시한다. 서지/초록/원문 접근 수준과 주장 확인 수준을 구분한다. 초록만 있으면 Figure·페이지·절 번호를 생성하지 않는다.
AI 해석, 출처 발췌, 사용자 확인, 미확인을 구분한다. 원문 확보만으로 주장 검증을 완료하지 않는다. 연구실 장비·가능성은 자료 없이 추정하지 않는다.
연구 공백 자동 발견, 과제 수주·랩미팅 통과 보장, 준비도/적합도 점수, 일정 관리, 자동 PPT 제작은 제외한다. 복잡한 그래프·연구자/기관 분석·새 논문 알림·장기 동향 추적은 후속 목록에 보존한다.

[단계와 기록]
P0=1~7: 기준 → 데이터 → 디자인 → 탐색 → 연구실/방향 → 준비 → 저장/내보내기 검증.
P1=8~11: 서버/인증 → 실검색 → AI → 피드백/버전/작업.
P2=12~14: PDF → 조건 비교/인쇄 → 통합 검증.
다음 파일을 만들고 이후 단계가 실제로 읽게 하라.
- docs/PRODUCT_CONTRACT.md: 위 목적·결정·금지사항·모드 경계.
- docs/PROGRESS.md: 14단계별 미착수/진행/구현/검증 상태, 수행 검사, 외부 미검증, 다음 입력 번호.
- docs/DECISIONS.md: 결정과 이유, 기존 파일 유지·교체 표.
- docs/TEST_MATRIX.md: 핵심 흐름과 검증 방법.
- docs/BACKLOG.md: 이번 제외 기능과 재검토 조건.
- README.md: 실제 실행법과 현재 가능한 기능.

각 단계는 지정 범위만 구현하고 자체 오류를 수정한 뒤 끝낸다. 다음 단계까지 자동 실행하지 않는다. 선행 기능이 빠졌으면 필요한 결손부터 보완한다. 외부 키 부재는 코드·고정 응답 검증과 실제 연동 검증을 구분해 기록한다. 서버 보안을 끄거나 가짜 성공으로 통과시키지 않는다. 보안·데이터 무결성 전제는 미완료 상태로 넘어가지 않는다.

[완료 기준]
현재 구조와 기존 작동 기능을 기록하고 위 문서를 생성한다. 이 단계에서는 제품을 전면 수정하지 않는다. 최종 답변은 확인한 저장소, 고정 결정, 남은 문제, ‘다음은 2번’으로 짧게 마친다.
