## 우선 보완할 결손과 근거

### 1. 새로고침이 기존 조사를 자동 복원하지 않고 새 조사를 만든다

- 근거: `src/app.js:83`, `src/app.js:96`, `src/app.js:488`.
- 브라우저 재현: EUV 시작 → 논문 1편 선택 → 저장 완료 → 새로고침.
- 관찰: 저장 목록이 **1개에서 2개**, 현재 화면 선택이 **0편**이 되었다.
- 기존 조사 자체는 저장 목록에 남아 있어 직접 열 수 있다. 영구 삭제나 완전한 데이터 유실로 표현하면 안 된다.
- 원인: URL 초기화가 저장된 프로젝트를 여는 대신 `search()`를 실행해 새로운 프로젝트 ID를 만든다. 기존 대표 E2E는 새로고침 직후 목록의 기존 항목을 열기 때문에 자동 복원·중복 생성을 검증하지 않는다.

### 6. 공통 데이터 계약과 모드 차단이 부분적이다

### 8. 비교 수치 연결과 근거 추가 동작이 부족하다

- 관찰: 화면은 선택 0편으로 돌아오고 DB의 `selPapers`도 `[]`. 이미 저장된 조사 전체가 지워진 것은 아니지만 마지막 변경이 저장되지 않는다.
- 원인: `openProject()`가 `cancelSave()`로 예약을 취소하고 이전 DB 내용을 읽는다. 전환 전에 변경을 저장하거나 변경 포기를 명시적으로 처리하는 경로가 없다. `goHome()`도 같은 취소 경로를 사용한다.
- 기존 새로고침 E2E는 저장 완료를 기다리므로 이 경우를 잡지 못한다. 단순히 같은 탭으로 이동하는 경우에는 발생하지 않는다.

### 남은 결손 2 — 일부 손상 자료에서 복구 화면과 저장 목록 모두 실패 (우선 수정)

- 파일: `src/schema.js:102`, `src/schema.js:115`, `src/state/record.js:90`, `src/repository/idb.js:41`, `src/controller/session.js:66`, `src/views/evidence.js:21`.
- 재현 A: 저장된 Claim의 `evidence[0]`가 `null`인 자료를 열기.
- 관찰 A: `Cannot read properties of null (reading 'id')`. 복구 제목은 없고, 저장 목록 전체가 “저장소를 읽지 못했어요”로 바뀐다. 다른 정상 조사도 목록에서 열 수 없다. 원본 데이터가 삭제된 것은 아니다.
- 원인 A: `validateClaim()`이 배열 요소를 검사하기 전에 `evidence.map(x => x.id)`를 실행한다. `validateRecord()` 자체가 예외를 던지면 `repo.list()`도 한 레코드에서 전체 실패한다.
- 재현 B: Evidence의 `location:null`인 자료를 열고 근거 보기.
- 관찰 B: `validateRecord()`는 정상으로 승인하지만 근거 패널에서 `Cannot convert undefined or null to object`가 발생한다.
- `claim.condition:null`도 정상 승인되며, 이후 질문 로직은 문자열 `.trim()`을 전제로 한다. 모든 배열 요소/nullable 필드의 검사를 보완하고 검증 함수가 오류 목록을 반환하도록 해야 한다.

### 남은 결손 3 — 정상적인 v1 비교 수정값을 새 형식으로 이전하지 못함 (우선 수정)

- 파일: `src/state/record.js:36`, `src/state/record.js:94`.
- 이전 앱의 셀 형식: `{value, history:[{at, by, value}]}`. 새 형식: `{cell:{value, unit, condition, evidenceId, ...}, history:[...]}`.
- 재현: `schemaVersion:1`, papers 스냅샷이 없고 위 구형 수정 셀을 갖는 정상 저장 레코드를 원래 버전 그대로 IndexedDB에 넣어 열기.
- 관찰: “저장된 조사를 열 수 없어요”, `cellEdits.example:euv-a|주요 결과: 구조 오류`. 원본 JSON 내보내기는 가능하지만 준비 화면에서 기존 수정값을 사용할 수 없다.
- `migrateRecord()`는 papers/userMeta와 버전만 보정하고 구형 셀과 이력을 변환하지 않는다. 현재 v0 테스트는 새 셀 형식을 유지한 채 papers 필드만 지우므로 실제 구형 셀을 검증하지 않는다.

### 남은 결손 4 — 없는 근거/논문 참조를 정상으로 승인

- 파일: `src/state/record.js:82`, `src/state/record.js:94`, `src/logic.js:142`, `src/logic.js:275`.
- 직접 재현: 셀의 `evidenceId:'ev:missing'`와 방향의 `readNext:[{id:'example:missing',title:'GHOST'}]`가 모두 검증 통과한다.
- 셀 근거는 참조된 ID의 존재·논문 일치 여부를 검사하지 않는다. 숫자 셀의 “근거 미연결” 표시는 ID가 비었는지만 확인하므로 없는 ID도 연결된 것처럼 취급될 수 있다.
- 방향의 papers ID는 검사하지만 readNext·대표/최근 문헌 등 다른 참조는 확인하지 않는다. 셀의 단위/조건/이력 타입과 scope 조건 배열의 요소 타입 검사도 부족하다.
- 정상 UI에서 임의 ID를 만들 수 있다는 주장이 아니라, 저장된 손상 자료를 무결성 검사에서 차단하지 못한다는 판정이다.

### 남은 결손 5 — 발표 가이드에서 논문 메모·수정값·조건 누락

- 파일: `src/logic.js:266`, `src/logic.js:325`, `src/views/prepare.js`의 내보내기 안내.
- 브라우저 재현: 논문만 선택 → 메모 `AUDITMEMO` → 주요 결과 `12345 nm`, 조건 `AUDITCONDITION` → 가이드 Markdown 받기.
- 관찰: 가이드에는 논문 제목이 있지만 위 메모·숫자·조건은 모두 없다. 한 페이지 요약에는 같은 내용이 정상 포함된다.
- `buildGuideMd()`는 제목과 미연결 경고만 사용하고, 실제 비교 셀의 값을 출력하지 않는다. “선택한 논문·메모·수정한 값이 파일에도 남는다”는 화면 안내와 구현자의 보완 설명을 모든 내보내기에 적용할 수 없다.

### 추가 계약 차이

- `src/providers/contracts.js:23`의 AnalysisProvider는 `analyze(project, papers) -> {summary, paperIds}`로 정의되어 있다.
- 실제 구현 `src/providers/analysis.js:25`는 `analyze({topicKey,papers,scope,userMeta}) -> {status,directions,count,reason,notices}`다. 현재 UI는 새 구현에 맞춰 동작하지만 “공통 인터페이스”의 선언과 구현은 일치하지 않는다. 이후 실제 공급자를 추가하기 전에 통일해야 한다.
- 11개 엔티티의 타입/검증 함수는 추가됐지만 위 손상/참조 사례까지 보호하는 완전한 계약이라고 평가할 수 없다.
- 방향 비교 표/카드의 근거 행은 여전히 “근거 논문 수”이며 실제 문헌/발췌 연결을 비교 안에서 제시하지 않는다. 모바일 카드 전환 자체는 통과했다.
