# Research Landscape 패러렐 UI/UX 평가와 Gemini 작업 지시서

작성일: 2026-10-27  
대상 프로젝트: `C:\Users\USER\Dev\Research_Page`  
대상 화면: `/parallel.html`

## 1. Gemini에 요청하는 작업

이 문서를 바탕으로 현재 프로젝트의 **패러렐 화면만** 개선하세요. 먼저 실제 파일을 확인하고, 아래 우선순위대로 구현·검증하세요. 별도 승인이 필요한 배포·설치·데이터 삭제는 수행하지 마세요.

가장 중요한 사용자 목표는 **연구군을 이해하고 무엇부터 읽을지 판단하는 것**입니다. 논문 선별, 원문 확보, Gemini에 자료 전달, 정리 결과 확인을 짧은 동선으로 연결하세요. 새로운 기능을 늘리기보다 화면의 역할과 우선순위를 바로잡으세요.

이 문서의 평가와 수치는 아래 고정 응답 검사에서 나온 것입니다. 실제 사용자 연구나 실제 논문 분석 결과로 표현하지 마세요. 제안된 화면 구조는 구현 권고안이며, 그 효과가 검증됐다는 뜻은 아닙니다.

## 2. 반드시 지킬 범위

- 사용자의 최신 지시: **앞으로의 변경은 패러렐 화면에만 적용한다.**
- 기본 화면 `/`와 `/index.html`의 디자인·동작·선택 정책을 변경하지 마세요.
- 공용 모듈을 수정해야 하면 패러렐 전용 분기를 두거나 전용 모듈로 분리하세요. CSS는 `body[data-layout="parallel"]` 아래로 한정하세요.
- 기존 조사, 논문 ID, 메모, PDF, 정리본, 근거, 백업 데이터를 보존하세요. 선택을 화면에서 숨기는 것과 데이터를 삭제하는 것을 구분하세요.
- 검색 공급자는 OpenAlex·Crossref입니다. Semantic Scholar를 추가하지 마세요.
- Gemini는 사용자가 PDF와 지시서를 직접 전달하는 외부 AI입니다. API 호출·자동 로그인·자동 전송을 추가하지 마세요.
- 프롬프트 생성, PDF 보관, AI 결과 가져오기, 사용자 확인은 서로 다른 상태로 표시하세요. 프롬프트를 만들었다고 분석 완료로 표시하지 마세요.
- 연구군은 수집한 자료 안에서 해석한 결과입니다. 분야 전체 구조·성장세·중요도가 검증됐다고 표현하지 마세요.
- 제공받은 단일 HTML의 Canvas 가상 API·가상 성공 처리를 실제 기능으로 가져오지 마세요.
- `research-landscape-prompts/` 원본 수정, reset, 자동 커밋을 하지 마세요.

작업 전 `AGENTS.md`, `docs/PRODUCT_CONTRACT.md`, `docs/PROGRESS.md`, `docs/DECISIONS.md`, `docs/TEST_MATRIX.md`, `docs/BACKLOG.md`를 읽으세요. 문서와 실제 구현이 다르면 실제 상태를 확인하고 차이를 기록하세요.

## 4. 평가 근거와 한계

2026-10-27 로컬 화면에서 가상 논문 30편을 고정 응답으로 넣고 Chrome으로 확인했습니다. 실제 검색·PDF 다운로드·Gemini 전송은 실행하지 않았습니다. 측정은 화면 높이 1000px 기준이며 콘텐츠와 폰트에 따라 달라집니다.

| 화면 너비 | 확인한 상태 |
|---|---|
| 1440px | 왼쪽 약 738px, 오른쪽 약 628px. 작업 패널은 상단 약 380px부터 시작. 원문 확보 제목 약 4358px, Gemini 정리 제목 약 4744px에 위치 |
| 1024px | 좌우 패널이 세로로 쌓임. 랩미팅 준비가 약 5540px에서 시작 |
| 375px | 랩미팅 준비가 약 6608px에서 시작. 원문 확보 약 5256px, Gemini 정리 약 5710px에 위치 |
| 30편 비교표 | 내부 너비 약 1951px. 1440px 화면에서 보이는 표 영역은 약 624px. 제목이 좁은 열에서 과도하게 줄바꿈됨 |

페이지 전체의 가로 넘침은 없었습니다. 논문 선택이 오른쪽에 반영되고 메모·저장본이 유지되는 것은 기존 검사에서 확인했습니다. 오른쪽 패널을 300px 스크롤한 뒤 선택 변경 시 스크롤도 300px로 유지됐습니다. 스크롤이 초기화된다고 주장하지 마세요.

스크린샷은 저장소 기준 다음 파일입니다. Gemini에 저장소 접근 권한이 없으면 사용자가 해당 이미지를 별도 첨부해야 합니다.

## 5. 평가와 우선순위

### P0 — 30편 전체 비교를 기본 동작에서 분리

**관찰:** 검색 결과 30편이 선택되고 오른쪽 비교표와 메모에 모두 들어갑니다. 좁은 열에서 제목과 버튼이 길게 줄바꿈됩니다.

**해석:** 자료 수집과 몇 편의 상세 비교가 하나의 선택으로 묶여 있어, 사용자가 선별하기 전부터 복잡한 표가 만들어집니다.

**작업:**

- ‘수집한 논문’, ‘Gemini 정리에 사용할 논문’, ‘서로 비교할 논문’을 구분하세요.
- 기존 정리용 선택·일괄 원문 받기를 유지하면서 **패러렐 전용 비교 대상**을 따로 두는 방식을 우선 검토하세요. 공용 자동 선택 정책을 바꿔 기본 화면에 영향을 주지 마세요.
- 비교는 2~4편을 명시적으로 고른 뒤 보여주세요. 선택 전에는 짧은 안내만 표시하세요.
- 4편이 넘어가면 비교 대상 교체를 안내하고 기존 선택을 조용히 지우지 마세요.
- 논문 ID를 재사용하고 [P#]와 실제 논문의 대응 관계를 유지하세요.
- 비교 제목·열 너비를 확보하고 필요한 경우 표 내부에서만 가로 스크롤하세요. 데이터가 없으면 미확인으로 남기세요.

### P0 — 오른쪽 영역을 ‘현재 작업’에 배정

**관찰:** 사용자는 논문을 선별하는 중인데 오른쪽에는 랩미팅 비교표·메모가 먼저 나옵니다. 핵심인 Gemini 정리는 왼쪽 긴 목록 아래에 있습니다.

**작업:**

| 왼쪽: 자료 탐색 | 오른쪽: 현재 작업 |
|---|---|
| 논문 필터와 목록 | 선택 논문 상세 |
| 선택·원문 확보 상태 | 이번 정리의 초점 |
| 정리 대상·비교 대상 지정 | Gemini 지시서 생성·결과 가져오기·결과 확인 |
| 자료 추가와 탐색 | 요청했을 때 비교표·랩미팅 준비 |

- 오른쪽 기본 작업은 ‘연구군·읽기 순서 정리’로 두고, 논문 상세·비교·랩미팅은 같은 영역에서 전환하게 하세요.
- 기존 정리 섹션을 옮겨 사용하세요. 같은 입력칸과 DOM ID를 양쪽에 중복 생성하지 마세요.
- 프롬프트 복사 → PDF 직접 첨부 → 정리 시작 → 결과 가져오기 흐름을 한 영역에서 안내하세요.
- 실제 AI 결과를 가져오기 전에는 예시 연구군이나 추천 순서를 실제 결과처럼 채우지 마세요.
- 원문 확보는 왼쪽 상단 도구 또는 고정된 상태 영역에서 접근할 수 있게 하세요. 30개 행 아래까지 내려가는 것을 필수 동선으로 만들지 마세요.

### P0 — 모바일·좁은 화면은 작업 전환을 기본으로

**관찰:** 1120px 이하에서는 긴 두 패널을 세로로 쌓아 후속 작업까지 이동 거리가 커집니다.

**작업:**

- 1120px 이하에서는 ‘논문 / 정리 / 비교·발표’처럼 짧은 작업 전환을 기본으로 제공하세요.
- 비활성 작업 전체를 페이지 아래에 이어 붙이지 마세요.
- 전환 시 논문 선택, 입력 중인 초점·메모, 비교 대상, 저장본을 보존하세요.
- 큰 화면에서는 탐색과 작업을 좌우로 보여주세요. 작은 화면에서 좌우를 강제하지 마세요.

### P1 — 상단과 이동 체계 정리

- 검색 이후에는 입력 영역을 ‘현재 주제 · 수정’으로 접으세요. 수정 버튼으로 다시 펼칠 수 있어야 합니다.
- 주제·범위 설명을 좌우에 반복하지 말고 공통 작업 헤더로 모으세요.
- ‘좌우 함께 보기’가 현재 상태인지 다음 행동인지 모호합니다. ‘분할 보기 / 탭 보기’처럼 선택 상태와 행동을 분명히 표시하세요.
- 단계 링크, 탭, 랩미팅 이동 버튼의 역할을 통일하세요. 실제로 없는 단계는 완료처럼 표시하지 마세요.
- 선택·원문 상태 표시줄은 모바일에서 필터·버튼·내용을 가리지 않게 하세요.
- PC 연결·폴더 경로·도서관 프록시 같은 설정은 필요한 시점에 열도록 접고, 현재 작업의 주 행동보다 강조하지 마세요.

## 6. 완료 기준

### 기능과 데이터

- 기본 화면의 기존 기능·레이아웃·선택 정책이 유지된다.
- 검색 결과 30편을 넣어도 비교표에 자동으로 30편이 들어가지 않는다.
- 정리용 선택과 비교용 선택이 서로 의도치 않게 바뀌지 않는다.
- 기존 선택·메모·PDF·정리본·ID 대응이 화면 전환과 저장본 재열기 뒤에도 유지된다.
- Gemini 정리와 원문 받기에 접근하려고 논문 목록 30편 끝까지 스크롤할 필요가 없다.
- 비교표는 선택된 2~4편을 읽을 수 있는 열 너비로 표시한다.
- AI 결과가 없는 상태, PDF 일부 확보, 원문 실패, 저장 실패를 성공 상태와 구분한다.

### 화면과 조작

- 1440px에서는 좌우 화면이 함께 보이고, 현재 작업과 주 행동을 바로 찾을 수 있다.
- 1024px와 375px에서는 작업 전환으로 이동하며 긴 두 패널을 세로로 쌓지 않는다.
- 페이지 전체의 가로 스크롤이 없고, 필요한 비교표 스크롤은 해당 영역 안에 한정된다.
- 키보드로 작업을 전환하고 입력할 수 있다. 선택 상태와 패널의 접근성 속성이 일치한다.
- 고정 헤더·표시줄이 주요 입력과 버튼을 가리지 않는다.
- 같은 입력을 다른 위치에 복제해 상태가 어긋나거나 ID가 중복되지 않는다.

### 검증과 보고

- `npm run check`와 변경에 관련된 검사를 실행한다.
- 패러렐 E2E에 30편 상태, 비교 대상 분리, 정리 접근, 작은 화면 전환, 입력 보존을 반영한다.
- 기본 화면도 대표 흐름을 확인해 공용 코드 변경의 영향을 검사한다.
- 1440px·1024px·375px에서 스크린샷을 만들고 직접 확인한다. 가로 넘침 없음만으로 가독성 검사를 대신하지 않는다.
- 고정 응답 검사와 실제 외부 연동을 구분한다. 이번 UI 검증 때문에 실제 논문 다운로드나 외부 AI 전송을 추가하지 않는다.
- 완료 후 `docs/PROGRESS.md`와 필요한 검증 기록을 갱신한다.

## 7. 권장 작업 순서와 최종 보고

1. 현재 코드와 문서를 읽고 공용 선택 상태가 사용되는 경로를 파악한다.
2. 패러렐 전용 작업 영역과 비교 선택 상태를 설계한다.
3. 30편 자동 비교를 분리하고 정리 기능을 오른쪽 작업 영역으로 옮긴다.
4. 작은 화면 전환과 상단 축소를 적용한다.
5. 데이터 보존·기본 화면 회귀·반응형 화면을 검증한다.

마지막에는 변경한 파일, 개선된 사용자 흐름, 실행한 검사와 결과, 남은 제한을 짧게 보고하세요. 배포하지 않았다면 배포 완료라고 쓰지 마세요. 저장소를 직접 수정할 수 없는 환경이라면 파일별 변경안이나 적용 가능한 패치를 제공하고, 구현·검증했다고 주장하지 마세요.
