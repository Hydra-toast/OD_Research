## 검사 방식

1. 사용자 데이터와 분리된 테스트 저장소에서 example: ID와 “가상 예시 · 실제 논문 아님” 표시를 가진 고정 자료를 사용한다.
2. 기존 테스트와 설정을 확인하고 checkJs, 관련 단위 검사, 패러렐 E2E, 기본 화면 대표 흐름 회귀를 실행한다. 바뀐 UI 기대값은 고치되 데이터·접근성 검증을 삭제하지 않는다.
3. 코드 검사만으로 완료하지 말고 실제 브라우저에서 30편 상태를 렌더링한다. 각 크기의 스크린샷을 남겨 글자·스크롤·작업 접근을 확인한다.
4. 목록의 첫/마지막 행, 마지막 컨트롤, 좁은 화면 복귀 위치, 진행 갱신 중 입력, 저장 실패 후 재시도를 확인한다. 실패 처리는 고정 응답으로 재현해도 되며 검사 방식은 명시한다.
5. 기본 화면과 패러렐의 같은 시나리오를 비교한다. 폭·본문·기본 버튼 크기와 페이지/패널 스크롤을 각각 기록한다.
6. 기본 검색·초록/메모 열기·원문 시작·프롬프트 복사·결과 가져오기의 클릭/필수 입력을 센다. 이전 버전을 실제 측정하지 않았다면 추정치를 실측으로 보고하지 않는다.
7. 결함을 수정하면 관련 검사와 영향을 받은 기본 흐름을 재실행한다. 통과 뒤 이유 없는 반복 검사를 하지 않는다.

실제 검색·실제 PDF 다운로드·Gemini 계정·응답 품질 검증은 이번 자동 검증에서 실행하지 않는다. 고정 응답 성공을 외부 연동 성공으로 보고하지 않는다. 실행 환경 제약은 해당 항목에 명시한다.
